# 闸门卡片采用分层默认与整卡裁决，聊天修订是未决内容的统一修改通道

品牌知识抽取确认卡曾要求用户逐条勾选表态（最多 50 行、每行带摘录与置信度），确认负担远超必要。参照 js_ai dev 分支 `ProfileFactList` 的复核模式，闸门卡片改为「字段行 + 分层默认」：材料原文行视为已就绪、零控件；AI 补全行只带一个纯视觉的逐行「确认」；冲突行显式二选一，未全部解决前整卡确认禁用；行内不再展示摘录与置信度。一次整卡确认即构成对全部未决内容的用户裁决并**全量采纳**（含从未被逐条查看的 AI 补全行）；`decide-batch` 服务端逐条独立事务的语义不变，只是确认粒度从 per-fact 降为整卡。

同时卡片 UI 不再提供拒绝/删除。未决内容的修改（改、删、增）统一收敛为聊天自然语言显式指令：Agent 调用一个通用受限 MCP 工具作用于当前闸门的持久未决状态（一律记 `user-stated`、可审计），卡片经既有轮询/水合投影重渲染（≤3s），服务端改动覆盖卡片本地暂存。该工具一次交付即接入全部现有闸门；后续新增闸门必须接入同一工具，不得长出第二套修改入口。

## Considered Options

- **保留逐条勾选、仅优化视觉**：50 行每行一个待办，负担根因不除。
- **逐行确认做硬门（未理会的推断行按拒绝处理）**：用户必须滚动看完所有「待确认」行才能提交，仍是 N+1 次动作；用户明确选择全量采纳换取一次点击。
- **外部编码代理式「打字打断、拒绝重跑」**：那类确认卡挂的是一次未执行的工具调用；本产品（小鲸同学）的闸门内容是持久状态（候选已落 SQLite、问题池挖词花真实 provider 费用），重新生成成本高且不确定。故打字必须经受限工具直达持久状态，而非打断重跑。
- **聊天修订复用 `propose_brand_fact` 制造冲突行**：一句话的事变成「提议 → 等冲突 → 卡片二选一」三步，且冲突语义被滥用为通用编辑通道。
- **每个闸门一个专用修订工具**：N 条 Agent 纪律、N 份契约；单入口按闸门类型分发的成本更低。

## Consequences

- 低置信 AI 补全可能在从未被滚动查看的情况下随整卡确认进入品牌权威库；卡片阶段无删除，纠正通道只有：卡片「更改」、聊天修订、后续冲突提案 + 版本史。这是用一次点击换确认负担的显式代价。
- 「候选写权威前必须经用户确认」不变量保留，但其粒度从逐条动作降为整卡一次动作；`knowledge_authority.md`、`material_import.md` 已同步修订。
- 逐行「确认」按钮是纯视觉糖（本地状态），必须按候选 id 扛住 3s 轮询的投影重建；卡片「更改」同样暂存不落库，随整卡确认一并提交。
- 零点击自动采纳被明确否决：哪怕整卡全部为材料原文、零冲突，也必须点一次确认。
