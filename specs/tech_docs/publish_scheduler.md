# GEO deterministic publishing

Ticket 13 turns one confirmed distribution-plan revision into a durable, user-authorized execution. `PublishScheduler` is an application-lifetime Rust owner backed by the BrandWorkspace SQLite database. It does not use a Session Sidecar timer, an HTTP request, or a Renderer tick to make future work run.

## Authority and confirmation

Node and the model may read `latest`, read an exact execution, and prepare a preview. Paid-action mutations are absent from the Sidecar and Rust Management API. Confirmation, start, and explicit safe-item retry are WebView-only Tauri commands. Ticket 12 confirmation is not execution authorization: the Ticket 13 card shows the exact approved article revision/hash/summary, frozen distribution plan revision, channels, known price and rate, budget, schedule, provider snapshot, and irreversible impact before accepting a separate user checkbox and confirmation gesture.

An awaiting preview may be superseded by a new confirmed distribution plan. The old preview and its audit remain readable, but its never-executed internal idempotency keys are namespaced so the replacement can be prepared. Confirmed or started executions are immutable and cannot be superseded. The UI returns to a new editable Ticket 12 draft rather than modifying its confirmed artifact.

Chat revision (ticket 38, ADR 0003) adds exactly one Sidecar mutation seam for pending content: `/api/brand-publish-scheduler/revise` behind the shared gate tool (`gate=publish-preparation`, modify-only). It may adjust budget, publish start time, and per-item `scheduledAt` while the execution is still `awaiting-confirmation` and owned by the requesting session; Rust recomputes the confirmation digest over the stored snapshots with the same shared formula (preview and revision build one `confirmation_digest_of`), bumps the revision, and appends a `revision` audit row carrying the verbatim user instruction. The old digest fails closed at confirmation, so the user must re-check and re-authorize the new digest through the UI command; confirmation, start, and retry remain WebView-only. The authorization card re-polls `/publish-scheduler/latest` every 3s while pending and resets the irreversible-impact checkbox whenever the digest changes. The payload hash never covers `scheduledAt`, so a schedule revision does not invalidate the frozen order payload.

The `prepare_publish` tool result is part of the chat transcript and returns only a slim points-only projection (`PublishExecutionCardProjection` in `shared/geo/publishScheduler.ts`: `budgetPoints` / `totalPricePoints` / per-item `pricePoints`, schedule, digest and irreversible impact): CNY amounts (`budgetCny`, `estimatedSpendCny`, per-item `estimatedPriceCny`) and the conversion rate never enter chat, so the model can only quote points (see `system_prompt_architecture.md` for the matching prompt rule). `PublishAuthorizationGateCard` hydrates the slim envelope into the full projection shape at parse time (neutral defaults for missing fields — provider snapshot slots are marked unconfigured rather than asserted — and the budget back-converted with the exact-inverse `pointsToCny`), and the 3s `/publish-scheduler/latest` poll replaces it with the authoritative projection. Chat budget revisions likewise pass `budgetPoints` and are converted server-side; legacy `budgetCny` patches from older transcripts stay accepted.

## Stable item and payload contract

The execution unit is one approved article × one assigned channel. Each row freezes the approved revision/body hash/path, channel/resource snapshot, distribution plan and revision, schedule, estimated price, provider configuration fingerprints, stable item ID, full internal idempotency key, and an external request `sn` of `publish-order-{sha256(internal-key)[0..32]}`. The external `sn` is at most 64 characters and remains stable across plan-only budget or schedule changes.

The worker also reads the frozen `perArticleMaxPoints` / `totalMaxPoints` from that exact confirmed distribution-plan projection and sends them with `executionId` / `itemId` to the operating gateway. Preview prices remain an early user-facing guard only. At actual order placement the gateway recalculates points from its latest authoritative resource price, rejects an item over the per-article cap, and atomically sums all frozen or settled orders for the same account + execution before enforcing the execution cap. The cap checks, balance check, and order freeze share one database transaction, so a post-preview price refresh or concurrent item cannot overspend the frozen limits.

The payload hash covers the exact order structure: external `sn`, channel kind/endpoint, resource ID, title, the deterministic object key (`content-key`; the public URL is resolved by the gateway at upload time), and the media or we-media structural fields. Internal `scheduledAt` is part of confirmation and the durable request summary, not the media order form. A same-key/same-hash unstarted preview can only be replaced through the explicit supersede flow; a started duplicate is rejected. A same-key/different-hash attempt fails closed. It never rewrites a submitted row, its external IDs, or its completed execution truth.

## Execution and recovery

The Rust background loop scans every BrandWorkspace for due persisted items. A SQLite immediate transaction performs claim/CAS with a claim token and lease. Earlier active sequence items block later ones. The provider path reads the bounded immutable approved file from the Rust-owned workspace, renders HTML, uploads to the frozen deterministic object key, then submits the channel order. Since the ticket-08 gateway closure both egress actions go through the execution's source Session Sidecar: the Rust executor attaches a `PublishExecutor(executionId)` owner (the same hidden-scheduler attach pattern the monitor scheduler uses) and calls the Sidecar's localhost egress routes (`/api/xiaojing/publish-scheduler/egress/upload|order`). Every such request carries the `x-xiaojing-account-token` header with the current fresh account access token (Rust refreshes it via the refresh-token rotation when the JWT exp is within the 120s margin), and the Sidecar prefers it over the birth-time admission env token — a scheduled item may fire hours after the Sidecar started. The Sidecar walks its typed ports to the operating gateway, which re-signs (OSS V1, supermedia HMAC-SHA256) and bills server-side; in direct mode it is a development fallback decided by the Sidecar transport, invisible to Rust. The idempotent order `sn` has a single authority in the Sidecar and is derived there from `distributionOrderSn(executionId, itemId)` — Rust only passes the ids. Egress results are classified values (`success` / `safe-retryable` / `non-retryable` / `unknown`, e.g. gateway 402 insufficient balance → non-retryable top-up semantics) that map one-to-one onto `PublishProviderOutcome`. No provider secret exists on the client at all; approved body bytes only enter the upload request. The order-status projection (`/api/xiaojing/publish-scheduler/orders`) only sends an item's derived `sn` to the gateway when the order exists there — primary signal `externalOrderId != null`, secondary a post-submit status (`submitted` / `failed-nonretryable` / `reconciliation-required`); unsubmitted items (including `failed-retryable` upload-stage failures, where no order was created) are projected with `status: null` and never queried, because the gateway's `order_not_found` would fail the entire batch.

Provider configuration fingerprints are non-secret hashes of the gateway egress identity frozen at preview (account session present + gateway base URL; server-side OSS/channel configuration is invisible to the client). The scheduler compares the complete snapshot before claim execution and the production transport re-derives the gateway identity immediately before each upload or submit egress. Missing session (not logged in) means the current side has no fingerprint, so a configuration change cannot be concluded: the comparison only bricks when both sides are configured and their fingerprints differ — a logged-out reconcile skips the executions untouched, and a logged-out claim is released and deferred (no retry budget consumed) to resume automatically once login restores. A changed gateway becomes fail-closed/unavailable or `reconciliation-required`; it cannot continue under an old idempotency key. The payload hash binds the deterministic object key (`content-key`), not a resolved URL: the gateway resolves the public URL at upload time, and the settled receipt URL must point exactly at the frozen object key (percent-decoded path equality) or the item requires reconciliation.

Expired upload claims may resume because the upload uses a stable object key. Expired submission claims are unknown outcomes and require reconciliation. Explicitly safe failures follow the authoritative 1 / 5 / 15 minute backoff with at most three retries. Provider rejection is terminal. Transport errors after a possible order submission, malformed success responses, server errors with unknown acceptance, and any same-key/different-payload conflict are never automatically retried. Submitted items and their external content/order IDs remain immutable when later items fail (`external_order_id` is the gateway `partnerSn`, falling back to the derived `sn` when the upstream id is unknown).

### Reconciliation resume channel

`reconciliation-required` stops an execution even when nothing was ever submitted (e.g. upload-stage token expiry followed by a fingerprint inspection false positive). `retry_publish_item` only accepts `failed-retryable`, so a dedicated user-authorized recovery channel exists: `resume_reconciled_execution` (Tauri `cmd_publish_execution_resume_ui`, revision CAS like start/retry). It only accepts executions in `reconciliation-required` status — the projection invariant (any reconciled item forces the execution projection to `reconciliation-required`) makes "failed with reconciled items" unreachable. Three safety gates, in order: the current provider snapshot must be configured on both slots (logged in, otherwise `publish_provider_unavailable`); the frozen and current snapshots must not constitute a real configuration change via `provider_configuration_changed` (`publish_provider_configuration_changed`); and no item may carry an `external_order_id` — any submitted item has external side effects and must go through order-status reconciliation instead, so the whole execution is refused (`publish_execution_has_submitted_items`). Only never-submitted `reconciliation-required` items are reset to their pre-claim stage (upload stage → `pending`, submit stage → `uploaded`, matching the claim-time `object_url` stage split), with failure fields cleared, claim lease cleared, and `next_attempt_at_ms` set to now; the execution returns to `scheduled` with revision+1 and a `reconciliation-resumed` audit event. The renderer surfaces this as a 「恢复执行」 action on `PublishAuthorizationGateCard` (zh/en copy under `chat:publishResume`), which applies the authoritative returned projection and refreshes the balance projection on success.

Audit records contain bounded request summaries, timestamps, claim/result events, external IDs, and safe diagnostic codes. They exclude credentials, signatures, approved body bytes, and rendered HTML. Default tests use an injected mock Provider and deterministic clock plus a local mock-sidecar listener for the transport mapping; credentialed publishing smoke is forbidden in the normal test pool.
